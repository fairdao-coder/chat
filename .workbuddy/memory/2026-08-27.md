## SignalR SendPrivateMessage / SendGroupMessage 抛异常修复（用户报"服务端抛异常"）
- 根因：H5 客户端 `signalr.ts` 把 `type` 作为**字符串**（`'Text'/'Image'/'File'`）传给 Hub，但 `ChatHub` 的 `type` 参数是 `MessageType` **枚举**。SignalR 默认 hub 协议（JsonHubProtocol）**只认数字枚举**，字符串 `"Text"` 无法绑定到 `MessageType` → 在方法体执行前抛异常（"error on the server"），且不会写入 `Messages` 表（日志里无 `INSERT INTO "Messages"` 即为特征）。私聊与群聊都受影响，因为两者都有 `type` 枚举参数。
- 验证方法：临时在 Hub 加 `ILogger` + try/catch 打印异常并对比——传字符串 `type` 时方法体根本没进入（无 DBG 日志），传数字 `0` 时正常进入并走到好友/成员校验，从而确认是参数绑定阶段失败而非业务逻辑。
- 修复：`Program.cs` 的 `AddSignalR()` 改为 `AddSignalR().AddJsonProtocol(o => o.PayloadSerializerOptions.Converters.Add(new JsonStringEnumConverter()))`，使 hub 协议支持字符串枚举（与服务端其它接口用 string enum 的约定一致），客户端**无需改动**。已移除临时调试日志。
- 验证：重建服务端，用 node + @microsoft/signalr 复现——`private/group(string type="Text")` 与 `numeric` 均 OK；服务端日志无 error/exception。注：故意只传 2 个参数（省略 type）会失败，但真实客户端 `signalr.ts` 始终传 4 个参数且 `type` 默认 `'Text'`，不会触发。
- 遗留：H5 早前修复（api.ts 双重编码、Contacts.tsx 拦截、accept 用 userId）已构建到 `dist-build5`，本次为纯服务端修复，无需重新构建 H5。服务端目前以后台方式运行在 5298 供联调。

## MAUI Windows 构建根因修复（net10.0-windows10.0.19041.0 编译通过）
- **现象**：`dotnet build -f net10.0-windows10.0.19041.0` 仅在末尾报 `XamlCompiler.exe exited with code 1`（MSB3073），无任何其它错误，且 `bin` 为空、`obj/.../intermediatexaml` 为空、无 `.g.cs` —— 典型的「静默失败」。

- **修复点**：
  1. `Platforms/Windows/App.xaml.cs` 加 `using MauiChat;`（根因修复，生成器恢复产出）。
  2. 全部 8 个 XAML 根命名空间由 `…/2021/maui/xaml/2006` 修正为 `…/2021/maui`（之前从模板派生时填错）。
  3. `CollectionView` 误用 `ItemTapped` 事件（MAUI 无此事件）→ 改为 `SelectionMode="Single"` + `SelectionChanged`，事件处理签名改 `SelectionChangedEventArgs`（`ContactsPage`/`CreateGroupPage` 的 `.xaml` 与 `.cs`）。
  4. `LoginPage.xaml` 的 `Entry AutoCapitalization="None"` 在 MAUI 不存在 → 删除该属性。
  5. `ChatPage.xaml.cs` 把 `[QueryProperty]` 误标在属性上（MAUI 该特性只能标在 class）→ 移到 `class ChatPage` 上。
  6. 4 个 ViewModel 用 `ObservableCollection<>` 却缺 `using System.Collections.ObjectModel;` → 补上。
  7. `AppShell.xaml` 的 `Shell.*` 品牌色用 `{StaticResource Primary/Panel}` → MAUI 源生成器**无法在编译期把 StaticResource/DynamicResource 解析成 Color 给 Shell chrome 附加属性**（已知 source-gen 限制，本地 `Shell.Resources` 也不行）→ 改为直接写十六进制 `#07C160`/`#F7F7F7`。颜色调色板同时内联进 `App.xaml` 的 `Application.Resources`（原在 `Resources/Styles.xaml`，`Styles.xaml` 内的隐式样式引用仍正常解析）。

## MAUI 多语言（中简/中繁/英/西）
- 需求：MauiChat 支持中文简体、中文繁体、English、Español 运行时切换。
- **架构**：RESX + 自研 `LocalizationManager` + `TranslateExtension` 标记扩展（不引入 CommunityToolkit.Maui 依赖）。
  - `Localization/LocalizationManager.cs`：单例；`ResourceManager("MauiChat.Resources.Strings", asm)` 取串；`SetCulture`/`Initialize` 改 `CultureInfo.CurrentCulture/CurrentUICulture` 并 `Preferences.Set("app_language", name)` 持久化；实现 `INotifyPropertyChanged`，切换时 `PropertyChanged(string.Empty)` 让所有 `{loc:Translate}` 绑定热刷新。设备语言→支持语言的映射（`MapToSupported`：zh-*→简体/繁体，es/en 直取，未知→en），中性 resx=English。
  - `Localization/TranslateExtension.cs`：**注意命名空间是 `Microsoft.Maui.Controls.Xaml`**（非 `Microsoft.Maui.Xaml`，否则 CS0234）；`IMarkupExtension<BindingBase>`，返回 `new Binding { Path="[Key]", Source=LocalizationManager.Instance }`，故语言切换时自动重求值。
  - RESX：`Resources/Strings.resx`(en 中性) + `Strings.zh-Hans/zr-Hant/en/es.resx`，共 ~60 键（UI 文案 + toast/alert/错误）。**不要**在 csproj 显式 `<EmbeddedResource>` —— .NET SDK 已默认把 `.resx` 纳入并自动生成卫星程序集（`bin/.../zh-Hans/MauiChat.resources.dll` 等），显式包含会触发 `NETSDK1022` 重复项错误。
  - `Converters/Converters.cs`：`OnlineTextConverter`/`DateBucketConverter`/`HubErrorTitleConverter` 改为走 `LocalizationManager`；新增 `FormatCountConverter`（联系人计数 `{0} conversations` 本地化，因 StringFormat 无法直接绑 Translate）。
- **接入口**：`App.xaml.cs` 构造里 `InitializeComponent()` 后调 `LocalizationManager.Instance.Initialize()`。XAML 加 `xmlns:loc="clr-namespace:MauiChat.Localization"`，文案用 `{loc:Translate Key=...}`（AppShell/ChatPage/ContactsPage/LoginPage/AddFriendPage/CreateGroupPage）。C# 端 toast/alert 用 `LocalizationManager.Instance["Key"]`。
- **语言切换 UI**：`LoginPage` 顶部加 `Picker`（4 语言，SelectedIndex→SetCulture）；`ContactsPage` 头部加 🌐 按钮→`DisplayActionSheet` 选语言。两者都即时刷新。
- **验证**：`dotnet build -f net10.0-windows10.0.19041.0` → **0 错误**；`bin/.../win-x64/{zh-Hans,zh-Hant,en,es}/MauiChat.resources.dll` 卫星程序集生成；`MauiChat.dll` 383KB、`intermediatexaml/MauiChat.dll` 206KB（源生成器对新 XAML 正常产出）。
- **已知限制**：转换器内的本地化文本（在线/离线、今天/昨天）只在源属性变化时重算，语言切换瞬间不会立刻刷新这些个别标签（下次数据变动才更新）；主 UI 文案/占位符/按钮即时刷新。不影响功能。

## MAUI 修复：Styles.xaml 的 StaticResource 解析失败（XamlParseException）
- **报错**：`Microsoft.Maui.Controls.Xaml.XamlParseException: Position 9:34. StaticResource not found for key Text`（解析 `Resources_Styles.xaml` 时抛，运行时 `InitializeComponent()`）。
- **根因**：`App.xaml` 把颜色调色板（`Text`/`Primary`/`Muted`/`Panel`/`Border`…）声明为 `Application.Resources` 的**直接条目**，再合并 `Resources/Styles.xaml`；而 Styles.xaml 的隐式 `Style` 用 `{StaticResource Text}` 引用。MAUI 的**合并字典是隔离作用域**——被合并的字典无法看到父 ResourceDictionary 直接声明的 StaticResource 键，于是运行解析失败。
- **修复**：把整个颜色调色板（15 个 Color）**移入 `Resources/Styles.xaml` 自身**（放在隐式样式之前），`App.xaml` 只保留对 `Styles.xaml` 的合并。这样颜色与引用它们的样式处于**同一** ResourceDictionary，StaticResource 在解析期即可命中。`ChatPage`/`ContactsPage` 等页面仍通过应用级合并字典正常解析这些键。
- **验证**：`dotnet build -f net10.0-windows10.0.19041.0` → **0 错误**（仅原有 MVVMTK 警告）。
- **可复用结论**：MAUI 中「颜色/笔刷等共享资源」与「引用它们的 Style/模板」必须放在**同一个**（或顺序更靠前的）MergedDictionary 里；不要把它们分散到父 ResourceDictionary 的直接条目 + 合并子字典。等价于 WPF 的经典规则：合并字典不能反向引用父字典的直接资源。

## MAUI 修复：点联系人打不开聊天窗口
- **现象**：联系人列表能正常显示，但点击任意联系人无任何反应，聊天窗口打不开。
- **根因**：`Views/ContactsPage.xaml` 的 `CollectionView`（x:Name=ContactsList）**漏接事件**——既没有 `SelectionMode="Single"` 也没有 `SelectionChanged="OnContactTapped"`，而 `ContactsPage.xaml.cs` 里的 `OnContactTapped(object, SelectionChangedEventArgs)` 负责执行 `OpenChatCommand` 并 `Shell.GoToAsync("chat?...")`。事件没绑定 → 点击根本不触发导航。
- **对比**：`CreateGroupPage.xaml` 的同类 CollectionView 已正确接 `SelectionMode="Single"` + `SelectionChanged="OnFriendTapped"`，说明这是 ContactsPage 单独丢失的一处接线（早前把 `ItemTapped` 改 `SelectionChanged` 时漏了 ContactsPage）。
- **修复**：在 `ContactsPage.xaml` 的 CollectionView 上补 `SelectionMode="Single"` 与 `SelectionChanged="OnContactTapped"`。`OnContactTapped` 内部已会在导航后清 `SelectedItem=null`，保证返回后可再次点击同一联系人。
- **验证**：`dotnet build -f net10.0-windows10.0.19041.0` → 0 错误。
- **经验**：MAUI 列表项点击导航的两种写法——① `CollectionView` 用 `SelectionMode="Single"` + `SelectionChanged` 事件；② 给行加 `TapGestureRecognizer`。用 SelectionChanged 时必须同时设置 `SelectionMode`（默认 None 不触发）**且**在 XAML 绑定事件处理，否则事件孤儿化、点击无反应。排查"点不动"类问题时，先看 XAML 是否真的把事件处理接上了。

## MAUI 修复：打开群聊报 "InvokeCoreAsync cannot be called if the connection is not active"
- **现象**：点开**群聊**（私聊正常）时抛 `System.InvalidOperationException: The 'InvokeCoreAsync' method cannot be called if the connection is not active`，栈在 `ChatViewModel.InitializeAsync` 第 69 行 `_hub.JoinGroupAsync(_targetId)`。
- **根因**：`Services/ChatHubClient.cs` 的 `Invoke` 只判断 `_connection is null`，没判断连接是否 **Active**。私聊打开时 `InitializeAsync` 不调用任何 hub 方法（历史走 HTTP），所以私聊没问题；群聊打开时要 `JoinGroup`，而此时 SignalR 连接可能处于 `Reconnecting`/`Disconnected`（掉线/重连中/刚登录还没就绪），`InvokeAsync` 直接抛异常。注意 `HubConnectionState` 枚举在本版 SignalR **没有 `Disconnecting` 成员**（只有 Connected/Connecting/Reconnecting/Disconnected），别引用它否则 CS0117。
- **修复**：
  1. `ChatHubClient` 新增 `EnsureConnectedAsync(timeoutMs=10_000)`：已 Connected 直接返回；若 Reconnecting 则轮询等待其落定（最多 timeout）；落定后若 Disconnected 则 `StartAsync()` 重启（WithAutomaticReconnect 在 start 失败时不自动重连，必须显式重启）；超时仍非活跃则抛清晰异常。`Invoke` 改为 `async Task`，先 `await EnsureConnectedAsync()` 再 `_connection.InvokeAsync`。Send/Join/Leave 全部复用，统一受保护。
  2. `ChatViewModel.InitializeAsync` 的 `JoinGroup` 外包 try/catch（失败弹 `Send_FailedTitle` + ex.Message），保证即使 hub 真的连不上，聊天窗口也能打开（历史已通过 HTTP 加载）。
- **验证**：`dotnet build -f net10.0-windows10.0.19041.0` → 0 错误 0 警告（首次增量报 2 错误是 `Disconnecting` 引用残留的陈旧状态，修正并_clean rebuild 后通过）。
- **经验**：SignalR 客户端在调用 `InvokeAsync` 前必须确保 `State == Connected`；对 Reconnecting 要等其落定、对 Disconnected 要显式 `StartAsync`。所有 hub 调用都应经过统一的"确保活跃"封装，不要裸调 `InvokeAsync`。

## MAUI 修复：发送消息仍报通用英文 "Failed to invoke 'SendPrivateMessage' due to an error on the server"
- **现象**（用户截图）：打开 test1 私聊、发"eee"，弹"发送失败 / Failed to invoke 'SendPrivateMessage' due to an error on the server."，仅一个"确定"按钮——而 `ChatHub.SendPrivateMessage` 对未好友应抛 `HubException("E_FRIEND_REQUIRED: 你们还不是好友...")`，客户端应据此弹"加好友/取消"的操作式对话框。
- **根因**：`server/ChatServer/Program.cs` 的 `AddSignalR` 把 `EnableDetailedErrors` 放在 `if (builder.Environment.IsDevelopment())` 里，**只在 Development 打开**。`Properties/launchSettings.json` 确实默认 `ASPNETCORE_ENVIRONMENT=Development`，但用户是用 `dotnet ChatServer.dll` 之类的命令把服务端以**后台进程**起在 5298（没走 launch profile），环境变量没设进去，落回 Production 行为 → SignalR 把 HubException 的消息原文**统一改写成**通用英文 "Failed to invoke '{method}' due to an error on the server." 后才发给客户端，错误码前缀 `E_FRIEND_REQUIRED:` 全部丢失，前端 `ReportSendErrorAsync` 的 `StartsWith("E_FRIEND_REQUIRED")` 全部 miss，落到兜底 `DisplayAlert(Send_FailedTitle, msg, OK)` 分支。
- **修复**：去掉 `IsDevelopment()` 守卫，**始终** `EnableDetailedErrors = true`。本服务端 Hub **只会** 抛出带 `E_*: ...` 用户提示码的 `HubException`（E_FRIEND_REQUIRED / E_TARGET_NOT_FOUND / E_BAD_TARGET / E_EMPTY），不含敏感信息，开着没有泄漏风险；不开则客户端永远拿不到错误码，操作式对话框就废了。
- **必做**：用户必须**重启**那个挂在 5298 的后台 server 进程才会生效（之前任务里服务端是后台跑的），改源码+rebuild 不够。
- **验证**：`dotnet build server/ChatServer` → 0 错误 0 警告。
- **经验**：SignalR 服务端对外抛出的 `HubException` 错误码是客户端业务流的一部分（前端按前缀分桶弹不同对话框/CTA），它**不是开发态才需要的"调试详情"**，所以 `EnableDetailedErrors` 不该无脑跟着 `IsDevelopment` 走。安全做法不是关掉它，而是配套 `IHubExceptionHandler` 拦截非 HubException 异常并打码，这样既保错误码传输又避免泄漏（.NET 8+ 才有 IHubExceptionHandler）。本次为最小修复直接全开；如以后担心泄漏可补一个 handler。
